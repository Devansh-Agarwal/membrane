# QM: weakness and integration research

Research date: 2026-09-27. Target: [yc-software/qm](https://github.com/yc-software/qm), public `main`. This is a source/documentation review, not a deployed acceptance test. The deployment package file reports `@yc-software/qm` **0.1.6**; the root private package reports 0.1.0. Neither is proof that all current-main features are included in a published image. A current immutable HEAD could not be verified; some fetched pages were cached from earlier September, so pin and check the exact release before implementation. [CLI package](https://github.com/yc-software/qm/blob/main/cli/package.json), [root package](https://github.com/yc-software/qm/blob/main/package.json).

## Main conclusion

QM is a credible execution and collaboration foundation. Its interesting weakness is the gap between **doing work** and **demonstrating that experience improved future work**. It already has memory, durable jobs, agent swarms, traces, custom models, and extension points. Rebuilding those would waste a demo. The promising addition is a visible loop connecting evidence, corrected memory, a trained specialist, and independently measured outcomes. That is a proposed integration, not a claim that the three products already implement the loop.

## What exists and should be reused

- **Multiplayer execution:** personal and shared scopes, Slack/web surfaces, scoped credentials and files, model/harness choice, scheduled work and webhooks, and publishable internal apps. Configuration, tools, skills and services can live in a deployment directory instead of a core fork. [README](https://github.com/yc-software/qm#readme).
- **Durable coordination:** documented swarms use regular durable QM sessions, worker transcripts, an outbox, idempotent spawn/message requests, execution leases, finite budgets, and worker approvals. These are implemented capabilities, not merely a proposal. Deployment needs Postgres session/run stores and sandbox inventory. [Swarm contract](https://github.com/yc-software/qm/blob/main/docs/swarms.md).
- **Memory with revisions:** the Postgres notebook has versioned captures/replacements, compare-and-swap updates, history and restore. Do not pitch GBrain as adding the first persistence or first memory-edit capability. [Postgres memory implementation](https://github.com/yc-software/qm/blob/main/src/memory/postgres-memory-service.ts).
- **Memory strategy evaluation:** QM already includes a notebook-quality benchmark scoring signal/noise, staleness and observation versus inference, with minimum floors. “QM has no evals” would be incorrect. This is narrower than proving that a trained model improves downstream task outcomes. [Memory benchmark](https://github.com/yc-software/qm/blob/main/src/memory/bench.ts).

## Concrete integration seams

### GBrain: an external provider, with an evidence-preserving bridge

QM's current supported interface is `MEMORY_PROVIDER_CONFIG`. The retired `BRAIN_*` settings are ignored. Routes independently control recall and automatic/explicit writes; local notebooks can remain the editable memory manager. This makes “keep personal notebook + retrieve organizational knowledge from GBrain” a natural composition. Current docs also describe a Memorable procedural-memory provider, so procedural recall is not categorically missing. [Memory-provider documentation](https://github.com/yc-software/qm/blob/main/docs/memory-providers.md).

The bridge should translate QM principals/scopes to GBrain permissions, implement the configured read/write MCP tools, and persist source IDs and revisions for the demo's evidence panel. Read/write credentials should be distinct. Avoid claiming a fully verified native GBrain integration: this review verified QM's generic MCP seam, not a live GBrain handshake. Existing deployment-specific GBrain servers may already fit it.

QM's router concatenates recalled provider text and merges exact query strings, while memory editing/history is delegated to the first managing provider. It does not itself provide a structured cross-provider contradiction adjudicator. A visible “new source supersedes old source” workflow is therefore an integration opportunity, not something to assume appears merely by connecting endpoints. [Router implementation](https://github.com/yc-software/qm/blob/main/src/memory/provider-router.ts).

### River: use custom providers before inventing a gateway

An admin can register a base URL, API key and model IDs using OpenAI Chat Completions, OpenAI Responses or Anthropic Messages. Secrets are stored separately; models enter the catalog and route through Pi. This is the simplest verified QM-side path for a River-hosted inference endpoint, conditional on River serving a compatible protocol. [Custom provider implementation](https://github.com/yc-software/qm/blob/main/src/model/custom-providers.ts).

The alternative `MODEL_GATEWAY_URL` integration auto-discovers only models advertised by both `/v1/models` and LiteLLM-style `/model_group/info` with valid tool/capacity/pricing metadata. Plain OpenAI-compatible inference alone is insufficient for automatic discovery; explicit compatibility mappings are supported. Gateway routes are Pi-only. A failed catalog refresh can disable gateway models after discovery has previously succeeded. Avoid adding this moving part for the first demo unless needed. [Gateway contract](https://github.com/yc-software/qm/blob/main/docs/model-gateway.md).

For an ambitious specialist, use River for a bounded classifier/extractor/ranker called as a QM tool instead of replacing the general reasoning model immediately. This is a proposed design that avoids assuming reliable tool use from a newly fine-tuned model. Tools and service plugins are standard deployment additions. [Deployment extension contract](https://github.com/yc-software/qm/blob/main/docs/deploy-directory.md).

### Traces and learning: build on real records

QM's session tape spec says phases 1–2 are implemented and serving by default. It includes message/tool history and request-envelope/usage/latency records, while project and foreign-harness cases retain reconstruction fallbacks. Therefore traces are usable raw material, but a universal perfect-replay guarantee would overstate the documented implementation. [Session tape specification](https://github.com/yc-software/qm/blob/main/docs/session-tape-spec.md).

**Proposed learning layer:** selected run → human correction → consent/scope check → sanitized training example → versioned dataset → River job/checkpoint → held-out comparison → explicit model promotion/rollback. Add run/source/dataset/model-version IDs to every displayed result. Do not train indiscriminately on transcripts or present a training job as measured improvement. This review did not verify a native end-to-end QM→River dataset/evaluation/promotion loop; that is an open integration question, not proof that no private deployment has one.

## Demo concepts grounded in these gaps

1. **Apprentice / Agent Dojo.** A QM agent attempts a task in a visible action simulator and makes a correctable mistake. A human demonstrates the right decision; GBrain stores the procedure and supporting evidence. River trains a narrow decision model, and a fresh QM agent attempts a separate transfer task. The UI compares baseline, memory-only and memory-plus-specialist variants. Passing previously failed held-out cases is the target demonstration, never a promised result before evaluation. A simulator makes actions inspectable and supplies objective outcome labels; text policy correction alone risks demonstrating only retrieval. This is the strongest combined story if River training latency fits rehearsal constraints.
2. **Organizational memory time machine.** Inject an outdated policy and then a dated correction. A graph/evidence panel highlights the conflicting sources, the affected decisions and the revision that wins. QM reruns the same task with an earlier versus current evidence snapshot. River classifies whether new facts invalidate prior decisions. Snapshot/version semantics need implementation or verification in GBrain; do not fake historical replay.
3. **Visible agent pit crew.** A mission board shows researcher, operator and reviewer QM sessions, their handoffs, tool results and approvals. Intentionally restart the coordinator, then show completion from durable state and the reusable lesson. River supplies a trained routing or quality specialist; GBrain supplies evidence and accepted lessons. The compelling missing product surface is the visible workflow plus measurement, not spawning many agents.

Voice can be a dramatic correction input for Apprentice: say “when this happens, choose this action,” then show the resulting procedure and training example before acceptance. Speech is an added interface; this review did not establish a native QM voice path.

## Practical build order and uncertainty

1. Pin one exact QM version and prove one model call plus one sandbox action, one durable run, and one artifact survives restart.
2. Prove GBrain read/write with two scopes and a forbidden cross-scope request; check returned source identifiers and timeout behavior.
3. Prove River inference through custom-provider registration or one dedicated tool; record real latency and streaming/tool-call behavior.
4. Add only the mission/evidence board and learning ledger needed for one narrative.
5. Prepare pre-trained checkpoints if training exceeds demo time. Label them as prepared artifacts; live scoring can still be real.

Deployment itself has nontrivial setup: provider-specific configuration, durable stores, sandbox runtime, web authentication and optional Slack credentials. The getting-started flow requires an owned cloud account and email/auth setup, and does not generate production deployment CI. Pre-provision the environment before judging whether the integration fits a short build window. [Getting started](https://github.com/yc-software/qm/blob/main/docs/getting-started.md).

Unverified here: exact current commit; installed deployment/version; GBrain's current compatible MCP auth and tool schemas; River's endpoint, training format, latency and tool-call support; existence of an upstream end-to-end training/promotion feature; real performance under the selected cloud/sandbox provider. These should become short integration spikes, not confident feature claims.
